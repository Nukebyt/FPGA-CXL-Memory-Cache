# Bug Log — CXL-Lite Memory-Side Cache

Discipline per the manual's §4.6: log every real bug here as it's found, regardless of how it was caught (sim, cross-tool lint, hardware bring-up). Bias/BI-handshake races turned out to be a rich source of bugs, as expected — but the two strongest stories in this log turned out to be about *hardware bring-up itself*, not RTL logic. Both are worth reading in full before anything else here.

Columns: **ID**, **Phase found**, **Found via**, **Summary**, **Root cause**, **Fix**, **Status**.

## Headline stories (read these first)

- **[BUG-006](#bug-006)** — the classic race-condition story. A one-cycle-latency Avalon shim design (`m2s_valid = write_fire && m2s_ready`) created a genuine deadlock the moment `m2s_ready` grew a dependency on software-resolvable state (bias/BI): the handshake needed to unblock the bus could never itself get bus access to complete. Found and fixed *before* it ever reached hardware, by reasoning through the design rather than by observing a hang.
- **[BUG-010](#bug-010)** (with **[BUG-009](#bug-009)** as its own honestly-corrected prequel) — the sharpest sim-vs-hardware divergence story in the project. Every board hang in this project traced to one cause — JTAG configuration is volatile, and an unconfigured FPGA fabric behind an *enabled* bus bridge stalls the CPU uninterruptibly — but it took four power cycles and a wrong turn (BUG-009: a real, separate reset bug, correctly fixed, but *not* the cause of the hangs it was originally blamed for) to find it. The self-correction in BUG-009's own entry is as much the point as the bug itself: a plausible root-cause theory that doesn't change the symptom when fixed needs to be abandoned, not defended.

## BUG-001

- **Phase found:** 1 (protocol engine, sim)
- **Found via:** Icarus Verilog cross-check (`iverilog -g2012`) — Verilator did **not** flag this
- **Summary:** `rtl/cxl_mem_protocol_engine.sv`, next-state logic used a ternary to assign an enum-typed signal: `state_n = m2s_valid ? MEM_ACCESS : IDLE;` (and the equivalent for `RESP`/`s2m_ready`). Icarus refused to elaborate: *"This assignment requires an explicit cast."*
- **Root cause:** Under strict IEEE 1800-2017 typing, a `?:` expression's result type isn't guaranteed to be treated as the enum type by every tool even when both branches are enum literals of that type — Icarus enforces this strictly; Verilator's default `-Wall` did not catch it, meaning **this class of bug is silently tool-dependent**: RTL that "works" in Verilator can fail to elaborate elsewhere (including, potentially, Quartus's synthesis-time elaborator later).
- **Fix:** Replaced both ternary assignments with explicit `if`/`else` inside the `case` arms. No functional change, purely a typing/portability fix.
- **Status:** Fixed. Re-verified: Icarus elaborates cleanly (one informational `unique`-qualifier-ignored notice, harmless), Verilator testbench still passes (`PHASE1 PASS: 4 writes, 5 reads, 0 errors`).
- **Why this is worth remembering for interviews:** it's a concrete example of why the roadmap's "cross-check in Icarus" step exists — single-simulator sign-off can hide portability bugs that only surface later (in a different sim, or worse, in synthesis).

## BUG-002

- **Phase found:** 1H (Avalon-MM shim, sim)
- **Found via:** Verilator functional testbench (`sim/phase1h/tb_avalon_shim.cpp`) — the very first run hung until a 100-cycle guard tripped: `TIMEOUT on avs_write addr=2`
- **Summary:** The testbench's `avs_write()` helper checked `avs_waitrequest` *after* calling `tick()` instead of *before*. Avalon-MM's `waitrequest` is sampled in the *same* cycle as `write`/`address`/`writedata` — a transfer completes on the clock edge where `waitrequest` was already low going in, not the edge after. Checking it post-tick meant the helper was asking "would a transfer starting now stall?" instead of "did the transfer I just asked for happen?", which produced the wrong retry decision and could livelock exactly when a request was accepted but the engine immediately went busy (which happens on essentially every `REQ_FIRE` write, since the engine leaves `IDLE` that same cycle).
- **Root cause:** Testbench bug, not an RTL bug — a backwards mental model of Avalon-MM's same-cycle `waitrequest` sampling semantics when writing the helper from scratch (the earlier Phase 1 testbench's `m2s_ready` polling loop had this right — check-then-tick — this one was written check-after-tick instead).
- **Fix:** `avs_write()` now calls `dut->eval()` after setting the request signals to settle `avs_waitrequest` for the *current* cycle, loops `tick()`+`eval()` while it's asserted, then does one final `tick()` for the edge where the transfer actually completes.
- **Status:** Fixed. Re-verified: `PHASE1H_SHIM PASS: register-interface write+read round trip verified`.
- **Why this is worth remembering for interviews:** it's a concrete illustration of how easy it is to get bus-handshake sampling edges backwards even in a testbench you just wrote — and a preview of exactly the class of timing reasoning the BI sequencer (Phase 4) will demand under much higher stakes. Getting `waitrequest`/`valid`/`ready` sampling direction wrong is a classic, recurring bug family across every handshake-based interface in this project, not a one-off.

## BUG-003

- **Phase found:** 1H (Qsys/HPS platform infrastructure)
- **Found via:** `qsys-generate` on the real project, then isolated by reproducing the identical failure on an untouched copy of the reference `de10_ghrd` project's `soc_system.qsys` (confirms this is a pre-existing environment issue, not something introduced by our design)
- **Summary:** `qsys-generate --synthesis=VERILOG` fails during HPS DDR3 SDRAM sequencer generation (the `hps_sdram` submodule's `seq` element, `altera_mem_if_hhp_ddr3_qseq`). The failing step shells out to `Nios II Command Shell.bat`, which on Windows requires WSL (`wsl bash -c '<nios2_command_shell.sh> make all'`) and runs `uniphy_mcc.exe` (the UniPHY Sequencer Microcode Compiler) followed by further recipe steps inside that WSL environment. The reported error is only ever the generic `child process exited abnormally` — `uniphy_mcc.exe` itself visibly completes its own work first (its log shows it reading `ac_rom.s`/`inst_rom.s` and writing `hps_AC_ROM.hex`, `hps_inst_ROM.hex`, `sequencer_auto_ac_init.c` successfully), so the actual failure is either `uniphy_mcc.exe`'s own exit code after that last logged line, or a *later* command in the same `make all` recipe — undetermined, because the intermediate build directory (under `%TEMP%`) is deleted on failure before it can be inspected.
- **Root cause (partially identified):**
  1. **Confirmed and fixed:** `nios2_command_shell.sh` gates on `uname -r` containing `"microsoft"` (true — we're inside WSL2) and then requires `wsl`, `make`, and `dos2unix` to all be present *on the WSL side* or it prints "Command 'X' not found" and exits 1 before doing any real work. Our WSL2 Ubuntu had `make` but not `wsl` (which cannot meaningfully exist inside WSL itself — it's the Windows-side control tool) or `dos2unix`. Reading the script confirmed neither is ever actually invoked for real functionality afterward — it's a pure presence check. Fixed by installing the real `dos2unix` (`apt-get install dos2unix`) and adding a no-op `wsl` stub at `/usr/local/bin/wsl` in WSL2 (documented inline in the stub itself as to why a stub is safe here).
  2. **Not yet identified:** even after that fix (confirmed reached further into the script — a follow-up test got past the gate to the script's `exec` logic), the exact same `uniphy_mcc.exe`/`child process exited abnormally` failure still reproduces identically, on both our modified project and the untouched reference project. So there is a second, distinct failure past the gate, somewhere in the `seq` module's `make all` recipe.
- **Fix:** Gate check (1) is fixed and verified. The underlying (2) is **not fixed** — this remains an open blocker to producing a full `.sof` for this design on this machine.
- **Status: FIXED (fully resolved).** By manually reproducing the `make mc` recipe outside Quartus's wrapper, found the real error hiding under the generic "child process exited abnormally": `make: *** [Makefile:27: mc] Error 9`. Ran `uniphy_mcc.exe` directly (bypassing `make` entirely) and confirmed it returns exit code **9** even though every one of its output files (`hps_AC_ROM.hex`, `hps_inst_ROM.hex`, `sequencer_auto_ac_init.c`) is present and correct — the tool completes its real work and then exits nonzero regardless, almost certainly from the `TBBmalloc: skip allocation functions replacement in ucrtbase.dll: unknown prologue for function _msize` warning it prints at startup (Intel TBB failing to hook a newer Windows UCRT than Quartus 21.1 (2021) was built against, causing a nonfatal-but-nonzero exit during teardown). Traced the Makefile-generating source to `C:\intelFPGA_lite\21.1\ip\altera\alt_mem_if\alt_mem_if_tcl_packages\gen\uniphy_gen.tcl` line 3828, which writes the `mc:` recipe without ignoring the exit code. **Fix applied** (by the user, with admin rights, after backing up the original): prefixed that recipe line with `-` — the standard GNU Make idiom to ignore a specific command's exit status — since the tool's actual output is confirmed correct regardless of its exit code. Original backed up to `uniphy_gen.tcl.orig_backup`.
- **Verified end to end:** `qsys-generate` now succeeds completely (`qsys-generate succeeded.`), and the full downstream flow (`quartus_map` → HPS SDRAM pin assignments → `quartus_cdb --merge` → `quartus_fit` → `quartus_asm` → `quartus_sta`) completed with 0 errors at every step, producing `output_files/CXL_DE10_Standard.sof` (7.4MB) with **positive timing slack on every corner and TNS=0.000** everywhere.
- **Why this mattered:** this blocked `quartus_map`/`quartus_fit`/`quartus_asm` from ever running to completion on this machine, **independent of anything in our CXL design** — confirmed by reproducing the identical failure on the untouched reference project before any fix was found. `cxl_avalon_shim` itself generated with zero errors of its own throughout.
- **A second, unrelated red herring investigated and ruled out along the way:** `systemd=true` was also found set in WSL2's `/etc/wsl.conf`, which the fpga_checklist.md correctly flags as a general risk to Windows-interop reliability. It was changed to `systemd=false` (harmless, checklist-endorsed either way) but direct testing (`/mnt/c/Windows/System32/cmd.exe /c echo hello` succeeding) confirmed WSL-to-Windows interop was never actually broken in this environment — the real bug was uniphy_mcc.exe's own exit code, not an interop failure. Worth recording: don't let a plausible-sounding checklist rule substitute for verifying the actual failure directly.

## BUG-004

- **Phase found:** 2 (outstanding-transaction tracker, RTL authoring, caught before ever simulating)
- **Found via:** Code review while writing the module, following the same discipline as the fpga_checklist.md's own "multiple drivers" warnings — not caught by a tool, caught by re-reading the design before building it.
- **Summary:** An early draft of `cxl_mem_protocol_engine.sv`'s Phase 2 rewrite drove the `slot_valid`/`slot_cnt` per-tag arrays from **three separate `always_ff` blocks** (one for accepting new requests, one for the countdown decrement, one for clearing a slot on response-consume). Two or more procedural blocks driving the same signal is illegal for synthesis and undefined even in simulation — this would have been a "multiple drivers" elaboration error, or worse, silently wrong behavior depending on tool/simulator handling.
- **Root cause:** Designing the three concerns (accept / countdown / consume) as three independent pieces of logic without first checking they don't all touch the same storage.
- **Fix:** Consolidated all per-slot state into **one** `always_ff` with a single per-tag priority chain (accept > consume > decrement > hold), so each array element has exactly one driver. Memory (`mem[]`) stayed in its own separate `always_ff` since it's a disjoint array with no such conflict.
- **Status:** Fixed before ever attempting to build — never actually manifested as a real failure, but would have been a synthesis-time error (or worse) if shipped as originally drafted.
- **Why this is worth remembering:** the multiple-driver rule is easy to violate by accident once a module's state is touched by more than one "concern" (accept vs. complete vs. timeout, etc.) — worth an explicit self-check ("does anything else in this module also drive this signal?") whenever a design grows past a single always_ff per piece of state.

## BUG-005

- **Phase found:** 2 (outstanding-transaction tracker, sim)
- **Found via:** Verilator testbench — only 4 of 5 expected responses arrived in the concurrent-request test; instrumented debug output (a temporary cycle-by-cycle print of `s2m_valid`/`s2m_tag`) showed tag 2's response happening and disappearing without ever showing up in the test's own captured results.
- **Summary:** The testbench held `s2m_ready = 1` constant for the entire test. Since the engine's response arbiter runs continuously and immediately consumes any response the moment it's offered (given `s2m_ready` is always high), a response that became eligible *while a later `fire()` call's internal wait-for-ready loop was still running* got silently arbitrated and consumed before the testbench's dedicated draining loop had even started watching `s2m_valid`. Not an RTL bug — the engine did exactly what an always-ready consumer asked it to do.
- **Root cause:** Treating `s2m_ready = 1` as a harmless "always accept" default, without considering that the testbench's own multi-step firing sequence (several `fire()` calls in a row, each internally advancing the clock) gives the DUT plenty of opportunity to produce and immediately lose events between the moments the testbench is actually paying attention.
- **Fix:** `s2m_ready` now starts low and is only raised inside each test's explicit drain loop, lowered again before the next multi-request firing phase. Documented inline in the testbench with the exact failure mode, not just the fix.
- **Status:** Fixed and reverified — all three Phase 2 tests pass (`PHASE2 PASS: out-of-order completion, multi-tag routing, and per-tag occupancy all verified`).
- **Why this is worth remembering:** this is a general trap for any testbench driving a "consumer ready" signal on a DUT with internal arbitration/queueing — an always-high ready signal isn't neutral, it actively changes when things happen relative to when the testbench is watching. The second time in this project a bus-handshake timing assumption produced a misleading result (after BUG-002) — worth treating as a pattern, not a one-off, when writing the next testbench.

## BUG-006

- **Phase found:** 4H (BI register interface, writing the shim-level testbench)
- **Found via:** Writing `sim/phase4h/tb_avalon_shim.cpp` — the test needed to fire a request to a Host-Biased address, then poll/write separate BI_STATUS/BI_REQ_ACK/BI_RSP_SEND registers to service the resulting BI handshake. Attempting this exposed that the two operations couldn't coexist on the shared Avalon bus at all.
- **Summary:** `cxl_avalon_shim.sv` wired `m2s_valid = write_fire && m2s_ready` to the engine — meaning the shim only ever asserts `m2s_valid` when the engine's `m2s_ready` is *already* high. As of Phase 4, `m2s_ready` also depends on bias/BI state (`m2s_ready = ... && (bi_state == BI_IDLE) && !bias_query_rd_data`), and the BI sequencer's `want_bi` trigger *itself* requires `m2s_valid` to be asserted to ever leave `BI_IDLE`. The result: for a Host-Biased address, `m2s_valid` can never be asserted (needs `m2s_ready`, which needs `bi_state==BI_IDLE` to stay true) and the BI handshake needed to *make* `bi_state` progress can never start (needs `m2s_valid`) — a genuine circular deadlock in the RTL, not a testbench artifact. Compounding it: even if that circularity weren't present, holding `avs_waitrequest` asserted on the REQ_FIRE address until the engine accepts would have blocked the *entire* Avalon bus for as long as BI resolution takes — and BI resolution is *itself* driven by software issuing further Avalon transactions (reading BI_STATUS, writing BI_REQ_ACK/BI_RSP_SEND). Software would have no way to ever unblock its own blocked bus.
- **Root cause:** The `m2s_valid = write_fire && m2s_ready` pattern was correct back when `m2s_ready` depended only on per-tag occupancy (Phase 1H–3H) — gating valid on an already-known-combinational-ready was harmless there. It silently became a deadlock the moment `m2s_ready` grew a dependency (BI state) that itself depends on `m2s_valid` having been asserted at all. Nothing about Phase 4's RTL review caught this in isolation — the sim testbench for the engine itself (`sim/phase4/`) drove `m2s_valid` directly as a true SystemVerilog input, sidestepping the shim's flawed wiring entirely, so BUG-006 was invisible until the shim-level register interface was actually exercised end to end.
- **Fix:** Replaced the shim's direct `write_fire`/`avs_writedata` wiring with a one-deep "pending request" holding register (`pending_valid_r`/`pending_is_write_r`/`pending_tag_r`), latched the cycle `REQ_FIRE` is written. `m2s_valid` is now driven from this latch independently of `m2s_ready`, and `avs_waitrequest` only stalls REQ_FIRE if the *holding register itself* is still occupied by an earlier unconsumed request — never on however long the engine takes to actually accept it. This decouples the Avalon bus transaction from the engine's acceptance latency entirely, so software stays free to service BI_STATUS/BI_REQ_ACK/BI_RSP_SEND on ordinary, unblocked bus transactions while a request sits latched waiting for BI to resolve.
- **Status:** Fixed and reverified — full regression suite (Phase 1/1H/2/3/3H/4/4H) passes, including the new `PHASE4H_SHIM PASS: BI register interface verified end to end`.
- **Why this is worth remembering:** a wiring pattern that's correct under one set of assumptions (ready is purely combinational and independent of valid) can become a genuine protocol deadlock once a later phase adds a dependency that violates that assumption — and it can hide successfully through an entire phase's RTL-level testbench if that testbench drives the interface directly rather than through the same intermediary (the shim) real software will actually use. This is the single most valuable bug this project has found — it's a coherence/liveness bug in the *interface design*, not an implementation slip, and it's exactly the class of bug the manual predicted would be the richest source of trouble once bias/BI logic exists (Part 4.6).

## BUG-007

- **Phase found:** 5 (cache), discovered during full-project regression after adding the cache — not in Phase 5's own new testbench, but in the *older* Phase 1 and Phase 3 testbenches, whose stimulus timing changed once cache eviction stalls entered the picture.
- **Found via:** Running the complete regression suite (all phases) after Phase 5/6 landed. Phase 1 and Phase 3 — both previously green for three phases running — started hanging. Isolated with live cycle-by-cycle debug traces rather than guessed at.
- **Summary — two distinct bugs, same root theme ("a testbench passing today doesn't mean its handshake modeling is actually correct, only that nothing yet exercised the part that's wrong"):**
  1. **Phase 1's `do_transaction`** never called `dut->eval()` after setting a new request's inputs, before checking `m2s_ready` in `while (!dut->m2s_ready)`. The *first* check of that condition therefore read a **stale value** — combinational output settled for the *previous* transaction's tag/address, not the new one. Harmless in every earlier phase, because readiness never actually varied (the engine was always immediately ready). Phase 5's cache made readiness genuinely depend on the newly-set address (an eviction stalls it), and the very write that happens to alias a cache index with an earlier one exposed it: the stale `m2s_ready` read as "ready" (leftover from the prior, unrelated tag), the code proceeded to the accept-edge tick as if the request had been accepted, deasserted `m2s_valid`, and then waited forever for a response to a request that had never actually been accepted.
  2. **Phase 3's Test 3** held `s2m_ready` high across firing *two* back-to-back writes to addresses that (as of Phase 5) alias the same cache index — a recurrence of **BUG-005**'s exact pattern (an always-ready consumer silently lets the engine's arbiter consume an early response before the dedicated draining loop starts watching it). This had always been present in the test; it only started failing once the second write's *eviction* stall widened the timing window enough for the first write's already-eligible response to be consumed and lost during it.
- **Root cause:** Both are testbench bugs, not RTL bugs — confirmed by writing an independent, from-scratch debug harness that exercised the identical stimulus correctly. Both are also instances of a bug family now seen four times in this project (BUG-002, BUG-005, and these two): a testbench's mental model of *when* a handshake signal is valid to read, or *when* it's safe to hold a consumer signal high, was subtly wrong, and stayed invisible until a phase added enough new timing variation to expose it.
- **Fix:** Added the missing `dut->eval()` before the first `m2s_ready` check in Phase 1's `do_transaction` (with an inline comment explaining exactly why, referencing BUG-002/005). Applied the same `s2m_ready`-gating fix from BUG-005 to both of Phase 3's Test 3 fire-then-drain sequences (writes and reads).
- **Status:** Fixed and reverified — full project regression (Phase 1, 1H, 2, 3, 3H, 4, 4H, 5, 6) passes clean.
- **Why this is worth remembering above the other three:** it's the clearest demonstration yet that a *passing* testbench is not the same claim as a *correct* testbench — these bugs sat latent through three, four, and five phases of continuous green results before a later phase's added timing complexity finally gave them a window to matter. The practical lesson: when a later phase changes timing behavior (adds a stall, a latency, a new stable-signal requirement), rerunning the *entire* regression suite — not just the new phase's own tests — is not a formality, it's how bugs like this get found before they reach hardware.

## BUG-008

- **Phase found:** 2H/3H/4H hardware bring-up (consolidated build) — a process/infrastructure finding, not an RTL or software bug.
- **Found via:** Reprogramming the FPGA fabric over JTAG (`quartus_pgm`) while the HPS was still running its earlier Linux session with an active SSH connection to it. Immediately afterward, the board became completely unreachable — 100% ping loss, not just SSH refusing to connect — before the new test program had even been copied over, let alone run.
- **Summary:** JTAG-reconfiguring the FPGA fabric resets *all* fabric-side logic, including the Avalon-MM slave interface (`cxl_avalon_shim`) sitting on the HPS's Lightweight HPS-to-FPGA bridge. If the HPS's bus interconnect has any live state referencing that bridge at the moment of reconfiguration — even just from earlier enumeration or a driver touching it, not necessarily an in-flight transaction from our own test program — the sudden fabric reset can wedge the bridge and hang the whole HPS side, taking down networking along with everything else. This matches a known, documented hazard class for HPS+FPGA SoCs: JTAG fabric reconfiguration is **not** transparent to a running HPS OS unless the system is specifically designed to tolerate it (e.g., holding the bridge in reset, or the OS re-enumerating fabric peripherals after reconfiguration) — this project's setup does neither, since Phase 1H's design never anticipated *re*-programming fabric while Linux was already up and talking to it.
- **Root cause:** Not a design defect in the CXL logic itself — a gap in the hardware bring-up *procedure*. Every previous JTAG reprogram this session either happened before Linux was ever booted against the current fabric image, or wasn't followed by live bus traffic quickly enough to hit the hang. This is the first time in the project a *re*-program happened with an already-active HPS↔FPGA-bridge session in progress.
- **Fix / status:** Requires a physical power cycle to recover — not something fixable or recoverable remotely. Reported to the user, who is checking the board.
- **Process lesson for future JTAG reprograms in this project:** either (a) reboot the HPS (or the whole board) immediately after any `quartus_pgm` that changes the fabric image, before resuming any HPS-side testing, rather than assuming the existing Linux session is still safe to reuse, or (b) if iterating on fabric-only changes with the HPS session intentionally kept alive, be aware this is a real risk and have a recovery plan (power cycle access) ready before doing it. Worth adding to the project's own pre-flight checklist going forward, the same way fpga_checklist.md's own §6 environment gotchas exist because someone hit them once and wrote it down.

## BUG-009

- **Phase found:** 2H/3H/4H hardware bring-up (consolidated build, first run after BUG-008's power cycle) — a real RTL bug, not process/infrastructure this time.
- **Found via:** Running the consolidated Phase 2H/3H/4H test on real hardware wedged the ENTIRE board (SSH refused, ping showed 80% loss / "Destination host unreachable" from the gateway) — not just the test process hanging. A `timeout 20` wrapper around the remote command also failed to recover it, indicating an uninterruptible hardware-level stall, not an ordinary software spin loop. Root-caused via code review (no board access needed) once two things were established: (a) `quartus_sta`'s `.sta.summary` for the currently-flashed build showed clean timing everywhere (all positive slack, TNS 0.000, including 9.87ns of setup slack on `CLOCK_50`), ruling out a timing-closure explanation; (b) `cxl_bias_table.sv` had no `rst_n` port at all — its only reset mechanism was a Verilog `initial` block.
- **Summary:** `initial begin for (i=0;...) bias[i]=1'b0; end` is a simulation-only construct. Verilator honors it perfectly (every sim testbench relies on address 0x09-style "never touched" addresses reading back Device-Biased at reset, and this always worked in sim). Real Cyclone V silicon gives no such guarantee for an inferred array with no explicit reset network — an address that was never `bias_write`'d could read back Host-Biased purely by chance on real hardware. `cxl_mem_protocol_engine.sv`'s `want_bi = (bi_state==BI_IDLE) && m2s_valid && bias_query_rd_data` would then trigger a genuine BI request on the very first M2S transaction of the whole test — before `test_phase4h()` (the only part of the test that acts as a host-side BI responder) ever runs. With nothing servicing it, `m2s_ready` for that tag never asserts, which leaves `cxl_avalon_shim.sv`'s one-deep `pending_valid_r` holding register permanently occupied. The *second* `fire()` call's `REQ_FIRE` write then hits `avs_waitrequest = write_fire && pending_valid_r` and blocks forever — a genuine stalled Avalon-MM bus transaction, which is a synchronous CPU-blocking hardware event, not a software loop. That plausibly explains why the whole board's networking died too (the ARM core doing the blocked MMIO store, and whatever else shares that L3/bridge path, wedges with it) rather than just the one userspace process hanging.
- **Root cause:** `cxl_bias_table.sv` had no synthesizable reset — reset-value correctness relied entirely on simulator-only `initial` block semantics with no hardware equivalent enforced.
- **Fix:** Added a real `rst_n` port, propagated from `cxl_mem_protocol_engine.sv`'s existing `rst_n`. Storage changed from an unpacked array (`logic bias [0:255]`) to a flat packed vector (`logic [255:0] bias`), so reset is a single-cycle `if (!rst_n) bias <= '0;` — no multi-cycle sweep, so no window where a real `bias_write` could collide with in-progress reset clearing. (An intermediate version of this fix used a 256-cycle sweep counter instead; it broke Phase 3/3H/4/4H sim regression because writes issued shortly after reset deassertion — which every existing testbench does — landed inside the sweep window and were silently dropped. Caught by the full-regression discipline before ever going near hardware again.)
- **Status:** Fixed, re-verified in sim (all 9 suites pass), and since **confirmed working on real hardware** — Phase 3H's bias set/get round trip passes on silicon, which exercises exactly this table.
- **⚠️ Correction — this was NOT the cause of the board hangs it was originally filed against.** The hangs were BUG-010 (accessing an unconfigured FPGA fabric). That was established afterwards: the hangs persisted *unchanged* after this fix was built and flashed, and were only explained once `/sys/class/fpga_manager/*/state` was found reading `power off`. The reasoning that led here — clean timing ruled out timing closure, and `cxl_bias_table.sv` genuinely had no `rst_n` — was sound as far as it went, but it stopped at the first plausible culprit instead of first confirming the fabric was even configured. **The lesson worth keeping: when a bug's symptom is "the whole system wedges," verify the platform is in the state you assume before hunting for logic bugs inside it.** The fix below is still correct and still worth having (an `initial` block genuinely is not a hardware reset), but it was fixing a *latent* bug, not the presenting one.
- **Why this matters for the interview writeup:** this is the sharpest sim-vs-hardware divergence story in the whole project so far — a bug that was structurally invisible to Verilator (which faithfully honors `initial` blocks) and only exists because real FPGA silicon doesn't give simulation's reset guarantees for free. It also demonstrates why BUG-006's holding-register design, while correct for its own stated purpose (decoupling bus timing from engine acceptance latency), doesn't provide a timeout or escape hatch — a `m2s_ready` that never comes for any reason, BI-related or not, given only ONE outstanding slot, blocks the Avalon bus itself. Worth flagging as a possible future hardening item (e.g., a hardware timeout with an error status bit) even though the current fix addresses the specific root cause.

## BUG-010

- **Phase found:** 2H/3H/4H hardware bring-up — a platform/procedure bug, and the actual cause of every board hang in this project (BUG-008 and the hangs originally attributed to BUG-009 are both this).
- **Found via:** Reading `/sys/class/fpga_manager/*/state` and `/sys/class/fpga_bridge/*/state` on the board — *after* four power cycles had been spent chasing RTL theories. The decisive readings:
  - `fpga_manager: power off` → the FPGA fabric was **unconfigured**
  - `br0 lwhps2fpga: enabled` → the Lightweight HPS-to-FPGA bridge was **enabled anyway**
- **Summary:** JTAG configuration (`quartus_pgm`) is **SRAM-based and volatile** — it is wiped by every power cycle — and this SD-card image's u-boot does **not** load an `.rbf`, so after any power cycle the fabric is empty. The bridges, however, come up enabled regardless. Any CPU access to `0xFF206000` (our shim) therefore goes out onto the Lightweight bridge toward a fabric with **no slave to respond**, and the Avalon transaction never completes. An ARM load/store to an unresponsive bridge stalls the core in an **uninterruptible** bus transaction: `SIGKILL`, `timeout(1)`, and the program's own software timeouts are all powerless, because execution never returns to software to check them.
- **Why it masqueraded as an RTL bug for so long:** three separate misleading signals.
  1. **The board still pinged and accepted SSH while "hung."** Cyclone V has a *dual-core* A9 — one core stalls on the bus, the other keeps Linux and networking alive. "Board is reachable" therefore proves nothing about bridge health, and it made the hang look like an application-level problem.
  2. **The stall is sticky across JTAG reprogramming.** Once a core is wedged on the bridge, programming the fabric afterwards does not retire the stuck transaction — only a full reboot does. So a "fix, reflash, retest" cycle kept reproducing the hang even when the fabric was, by then, correctly programmed. This is what made BUG-009's fix look like it had failed.
  3. **`fpga_manager` still reads `power off` even after a successful JTAG configuration** on this board/kernel, so the one status field that should settle the question reads misleadingly. It cannot be used to confirm configuration; only an actual (watchdog-protected) register read can.
- **Root cause:** Not a design defect — a missing precondition in the bring-up procedure. Nothing in the flow ever established "fabric is configured" as a prerequisite before HPS-side testing, because in earlier phases programming and testing always happened back-to-back within one power-on session, so the precondition was satisfied incidentally and never had to be stated.
- **Fix / procedure (now mandatory before any HPS-side test):**
  1. After **every** power cycle or reboot, run `quartus_pgm` **before** any program touches `0xFF206000`. The fabric is empty until you do.
  2. Program the fabric only when the HPS has **no stalled bridge transaction outstanding** — i.e. straight after a clean boot. If a hang already happened, reboot first; reprogramming alone will not clear it.
  3. **Arm `/dev/watchdog` before touching MMIO.** `sw/hps_driver/safe_probe.c` shows the pattern (set timeout, do the access, magic-close `V` to disarm). This converts a wedge from "user must physically power cycle" into an automatic self-reset, and it is what finally made hardware iteration cheap instead of costing a power cycle per experiment. All HPS test drivers now arm it.
  4. Confirm the fabric responds with a single watchdog-protected read before running a real test.
- **Status:** Fixed as procedure; hardware bring-up unblocked. Phase 2H/3H/4H all pass on real hardware immediately after applying it.
- **Why this matters for the interview writeup:** this is the strongest "debug the platform, not just the design" story in the project, and the most honest one. Four power cycles went into RTL theories (a bias-table reset, a timing violation, an address-map shift, stale partition reuse) for a bug that was never in the RTL — while the one cheap question, *"is the fabric even configured?"*, went unasked because programming it had always previously been implicit. The specific trap worth being able to explain: an uninitialized/unconfigured slave behind an enabled bridge doesn't fail fast, it hangs forever, and on a multi-core SoC that hang is partially invisible because the surviving core keeps answering pings.

## BUG-011 (documented limitation, not fixed — scoped out)

- **Phase found:** 7 (hardware stress testing) — found while debugging a Phase 7 test that appeared to fail.
- **Found via:** A stress test expected a fresh address to MISS the cache on its first post-BI touch and instead saw a HIT. Root-caused as a genuine test bug (the "fresh" address had already been populated by an earlier stress test's working-set sweep) rather than an RTL defect — but investigating it surfaced a real, separate coherence gap worth recording.
- **Summary:** The Avalon shim's debug-port bias write (`BIAS_SET`, Phase 3H, `write_bias` in `cxl_avalon_shim.sv`) can force any address to Host-Biased directly, with **no interaction with the cache arrays at all**. If a line is currently cache-resident (Device-Biased, possibly dirty) and something forces it Host-Biased via this debug path, the stale cached copy stays in `cache_valid`/`cache_tag`/`cache_data` completely untouched. A real host-initiated Device→Host bias transition would need to invalidate (and, if dirty, writeback) any device-side cached copy at exactly that transition — that's the whole reason bias exists. This path skips it.
- **Why this is scoped out rather than fixed:** the BI mechanism this project implements is deliberately one-directional — device-initiated (`want_bi` triggers when a device-side request hits a Host-Biased line, asking the *host* to invalidate its copy). A genuine host-initiated Device→Host transition (the direction that would need to invalidate the *device's* cache) was never implemented in either direction; `BIAS_SET` is explicitly a debug/test side-channel for directly poking table state, not a modeled protocol path, and its own header comment already frames it that way. Documenting this now so it's not later mistaken for a hardware bug if it resurfaces, and so a future extension implementing real host-initiated bias transitions knows this is the exact spot that needs a cache-invalidate hook added.
- **Status:** Documented, not fixed — out of the stated project scope (this project models the CXL.mem BI direction the manual scopes it to; a full bidirectional bias-transition protocol was never a goal). If ever extended: on a debug-forced or host-initiated Device→Host flip, the fix is to invalidate (and writeback if dirty) `cache_valid`/`cache_dirty`/`cache_data` at that address's index before committing the bias flip — reusing the exact same flush-then-proceed FSM pattern Phase 5's eviction and Phase 4's BI sequencer already establish.
- **Why this matters for the interview writeup:** a good example of a debug/test-only path not modeling the same invariants as the real protocol path, and of a stress test initially producing a confusing false failure that, once correctly root-caused, surfaced a real (if intentionally out-of-scope) design boundary rather than a bug. Also a good complement to the BUG-010 story: not every "looks like a hang/failure" investigation ends in a platform bug — sometimes it ends in "the test was wrong, AND here's a real edge worth knowing about anyway."

## BUG-012 (testbench bug, caught before it shipped)

- **Phase found:** 8 (hardware latency experiment) — a driver bug, not RTL.
- **Found via:** `gcc -Wall` on `host_driver_linux_phase8.c` — one `printf` call had two `%.1f` format specifiers but no corresponding arguments (a copy-paste of a long multi-string-literal message where the trailing `, diff, pooled_std);` got dropped). Undefined behavior: it printed whatever happened to be on the stack next to the format string, which on the first run looked plausible enough to be easy to miss (`(0.0 ns)`, `(3190.0 ns)` — the latter was actually a stray copy of an unrelated variable's value, not garbage-looking at all).
- **Summary:** the branch logic that DECIDES which conclusion to print (`fabs(diff) < pooled_std`) used the correct real values throughout and was never wrong — only the two numbers embedded in the printed message text were garbage. Caught before ever citing a wrong number, because `-Wall` was already part of every build command in this project's driver-compile discipline.
- **Fix:** added the missing `, diff, pooled_std)` arguments. Re-ran with `-Wall -Werror` to confirm zero warnings before trusting the output.
- **Status:** Fixed. Re-verified clean.
- **Why this matters for the interview writeup:** the sharpest possible illustration of why `-Wall` (and ideally `-Werror`) belongs in the build command for every measurement/reporting tool, not just RTL — a plausible-looking wrong number in a results printout is far more dangerous than an obviously-wrong one, and this one would have been very easy to quote in a writeup without noticing.

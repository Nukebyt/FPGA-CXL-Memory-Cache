# Coverage Report

Two independent sources, deliberately not conflated: automated Verilator line/toggle
coverage (a blunt, tool-generated signal), and a hand-curated functional cross-coverage
table mapping the manual's own suggested coverage model (Part 2, §"functional coverage
model") to the specific test that exercises each cell. The hand-curated table is the more
trustworthy artifact of the two — see the discussion of *why* below.

## 1. Automated Verilator line/toggle coverage

Generated by rebuilding all 7 engine-level testbenches (`sim/phase{1,2,3,4,5,6,8}`) with
`--coverage --trace`, running each, and merging the resulting `.dat` files with
`verilator_coverage`:

```
Total coverage (90/150) 60.00%
```
(Regenerated after §3's fix added a new test — up from an initial 87/150, 58.00%.)

Raw and unremarkable as a standalone number — a merged score across an entire module
mixes structural bookkeeping (interface ports, array declarations) with real control-flow
branches, and treats all of them as equally meaningful, which they aren't. What matters is
**why** each specific zero-coverage line is zero. Every one was checked individually,
categorized below, and none of them represent a functional gap in what was actually run —
**except one, which is real and stated plainly in §3.**

### Zero-coverage lines, categorized

**Toggle-coverage artifacts on wide signals/arrays (benign — the signals ARE exercised,
just never toggle across their full bit-width within these test patterns):**
- `dbg_cache_hits`, `dbg_cache_misses` (32-bit counters; test runs only ever reach values
  up to a few thousand, so high-order bits never toggle)
- `cache_dirty[]`, `cache_tag[]` (Phase 5/6/7/8 extensively read and write these arrays —
  toggle coverage wants every array element to see both 0→1 and 1→0 at every bit position,
  which 16-line/4-bit-tag arrays under directed (not randomized) testing won't fully reach)
- `slot_is_write[]` (same pattern — read and written on every accepted request, per
  `bugs.md` BUG-004's consolidated-`always_ff` discipline, just not toggle-exhaustive)
- `cxl_bias_table.sv`'s 256-bit `bias` vector (Phase 3/3H/4/4H/7 exercise specific
  addresses like `0x03`, `0x10`, `0x25`, `0x50`, `0xE0` — nowhere near all 256 addresses,
  so most bit positions of this packed vector never toggle)

**Intentionally, correctly zero — defensive "can't happen" arms:**
- `cxl_mem_protocol_engine.sv:141` — the BI FSM's `default: bi_state <= BI_IDLE;`. `bi_state`
  is a 2-bit enum with only 3 legal values (`BI_IDLE`/`BI_REQ`/`BI_WAIT_RSP`); the 4th
  bit-pattern is structurally unreachable under normal operation. Zero coverage here is
  correct, not a gap — it's the same category of defensive code a `default:` in a `case`
  is supposed to be.
- `cxl_mem_protocol_engine.sv:189` — the eviction FSM's equivalent `default:` arm.
  `flush_state` is a 1-bit enum (`FLUSH_IDLE`/`FLUSH_ACTIVE`) — a `default` arm on a 1-bit
  case with both values already handled is unreachable by construction. Same reasoning.

**Likely coverage-tool attribution artifacts, not functional gaps (flagged rather than
hidden or over-explained — the discrepancy is real and worth being honest about):**
- `cxl_mem_protocol_engine.sv:139` — `BI_REQ: if (bi_req_valid && bi_req_ready) bi_state <=
  BI_WAIT_RSP;`. Reported as zero, but this transition is *demonstrably* exercised —
  `sim/phase4`'s own test output ("BI request with correct address confirmed", "Atomic bias
  flip to Device-Biased confirmed") is functionally impossible without this exact line
  executing, and it passes on real hardware too (Phase 4H). Rather than guess at Verilator
  5.020's exact line-attribution behavior for non-blocking assignments inside case arms
  (plausible: the hit gets attributed to the `case` statement or the enclosing `always_ff`
  line instead of this one), this is reported as a known discrepancy between the automated
  tool and demonstrated behavior, not resolved further.
- `cxl_mem_protocol_engine.sv:234-235` — `arb_found = 1'b1; arb_tag = t[TAG_W-1:0];` inside
  the response-arbitration `for` loop. Same situation: every single passing test in this
  project drains at least one response, which is impossible without this exact assignment
  executing. Flagged as the same category of tooling artifact as above.

The pattern across both flagged lines — non-blocking/blocking assignments one level inside
a `case` arm or `for`-loop body — suggests a systematic attribution quirk in how this
Verilator version scores line coverage for that construct, rather than two unrelated
coincidences. Worth a deeper look if this project's coverage tooling gets more use, but not
chased further here since the hand-curated table below already independently confirms both
paths work, with named tests as evidence. (Confirmed once more after §3 below: a new test
added specifically to exercise the `BI_REQ` transition via a different trigger path still
shows zero on line 139, while `sim/phase4`'s own printed output for that exact test
confirms the transition happened. Consistent zero across two independently-triggered tests
of the same line makes "tool attribution quirk" a stronger explanation than "coincidence".)

## 2. Hand-curated functional cross-coverage

The manual's own suggested model (Part 2): `access_type × bias_state_before ×
bias_state_after`, and `cache_result (hit/miss/allocate/evict) × bias_state`. Each cell
below is backed by a specific test, not a generic "it's covered" claim.

| Access type | Bias before → after | Covered by |
|---|---|---|
| Read | Device-Biased → Device-Biased (no transition) | `sim/phase1`, `sim/phase3`, `sim/phase5` reads |
| Write | Device-Biased → Device-Biased (no transition) | `sim/phase1`, `sim/phase2`, `sim/phase5` writes |
| **Read** | Host-Biased → Device-Biased (BI-triggered) | `sim/phase4` Test 1, `sim/phase4h`, hardware `host_driver_linux_phase234h.c`, Phase 7 stress-4 |
| **Write** | Host-Biased → Device-Biased (BI-triggered) | `sim/phase4` Test 3 (added — see §3, was a real gap until fixed there) |

| Cache result | Bias state | Covered by |
|---|---|---|
| Miss → allocate | Device-Biased | `sim/phase5` (first-touch write), `sim/phase6`, `sim/phase8` |
| Hit | Device-Biased | `sim/phase5` (read-back), Phase 7 stress-4 (post-BI re-read) |
| Evict (dirty writeback) | Device-Biased | `sim/phase5`, `sim/phase6` (multi-round thrash) |
| *(any)* | Host-Biased | **Structurally impossible by construction, not merely untested** — `m2s_ready` is held low for a Host-Biased address until BI resolves (see `cxl_mem_protocol_engine.sv`'s own header comment: "by the time a request reaches the cache-allocate logic, Phase 4's bias gating has ALREADY forced it to be Device-Biased"), so a Host-Biased access can never reach the cache-hit/miss logic at all. This is a designed invariant, verified by the RTL's own accept-path gating (`m2s_ready = ... && !bias_query_rd_data && ...`), not a coverage cell that needs a test to fill it. |

### 3. The one real gap — found, and fixed rather than just written down

**A write to a Host-Biased line had never been used to trigger the BI handshake in any
test in this project**, checked directly rather than assumed: `sim/phase4`, `sim/phase4h`,
and Phase 7's `host_driver_linux_phase7.c` all used `is_write=0` (a read) for their
BI-triggering access.

The RTL's own trigger condition — `want_bi = (bi_state == BI_IDLE) && m2s_valid &&
bias_query_rd_data` — does not reference `m2s_is_write` at all, so by inspection a write
should behave identically to a read here. But "should, by inspection" is exactly the kind
of claim this project's own bug log (`bugs.md`) has repeatedly shown isn't good enough on
its own — BUG-009 and BUG-010 both trace back to an assumption that held in simulation but
wasn't actually verified against the real thing.

**Fixed, not just documented:** added Test 3 to `sim/phase4/tb_protocol_engine.cpp` —
marks a fresh address (`0x60`) Host-Biased, fires a *write* to it (`fire(dut, tfp, host,
true, 0x60, 5, 0xFEEDFACEu)`), and confirms: the response is a correct NDR (not DRS) with
the right tag; bias correctly flips to Device-Biased; and — the check that actually matters
most, since it's the one a race could break — a subsequent read confirms the written data
landed correctly, not just that the handshake completed. All pass. Full 11-suite regression
re-run clean afterward. The `access_type × bias_state_before × bias_state_after` table
above is now fully covered, not partially.

## Reproducing this report

```bash
# from sim/phaseN/ for any engine-level phase (1,2,3,4,5,6,8):
verilator -Wall --cc --exe --build -j 0 --coverage --trace \
    --top-module cxl_mem_protocol_engine --Mdir obj_dir_cov \
    -o Vcxl_mem_protocol_engine_cov \
    ../../rtl/cxl_bias_table.sv ../../rtl/cxl_mem_protocol_engine.sv tb_protocol_engine.cpp
./obj_dir_cov/Vcxl_mem_protocol_engine_cov   # writes coverage_phaseN.dat

# merge and annotate (run from within any sim/phaseN/ dir so the relative
# ../../rtl/ paths recorded in the .dat files resolve correctly):
verilator_coverage --write merged.dat coverage_phase*.dat
verilator_coverage --annotate annotated merged.dat
```

Each testbench (`sim/phase{1,2,3,4,5,6,8}/tb_protocol_engine.cpp`) includes
`verilated_cov.h` and calls `VerilatedCov::write("coverage_phaseN.dat")` right after
`tfp->close()` — that's the only permanent change made to enable this; everything else
above is a one-off build variant, not part of the normal `run.sh` flow.
